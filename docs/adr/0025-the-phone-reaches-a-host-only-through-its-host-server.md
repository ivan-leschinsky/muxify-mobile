# The phone reaches a Host only through its Host Server

Until now the phone reached a Host's Topics with one `muxify … --json` exec for each read and each write. It read the Listing on each focus and again after each write. It parsed the Host CLI's exit statuses, sent a write a second time itself (ADR 0021), and ran its own upload script. Desktop Muxify now talks to a Host through the Host Server, `muxify server` on one SSH channel, which pushes state as it changes (muxify-shell ADRs 0085–0091). We decide that the phone talks to a Host the way the Mac does. The phone keeps as little Host logic as it can. The Host CLI holds the rules, and the phone draws what its Host Server pushes.

- **One Host Server per Connection.** The registry of ADR 0012 opens it on its own exec channel as soon as the dial succeeds, with the `muxify` that the probe finds. It runs `'<muxify>' server`, skips the shell's output before `MUXIFY-PROTOCOL`, and exchanges `hello` (protocol 1, no nonce: the phone's Control Connection can never be the server's own Client). The server lives exactly as long as the Connection. The phone sends `ping` when it has sent nothing for 15 s, because the server exits after 45 s of silence.
- **Around the install.** The Host Server does not wait for the ADR 0016 install. When the install answers `installed` or `updated`, the phone sends `shutdown` and starts the server once more on the new binary. The new server's first items carry the whole state again. With no `muxify` on the Host yet, the Host Screen says "Installing Muxify on this Host…" until the install answers.
- **The phone draws pushed state.** The Host Screen draws the `snapshot` subscription, which is the computed `EnvironmentSnapshot` with `sidebar`. The Topic Screen and the Title Sheet draw a `topic` subscription with the Topic's detail. The phone holds no card, In Play or "read again" rule. The Host's Topics, Sessions and Unread reach the phone about one round trip after they change.
- **A focused Host Screen holds the Connection**, as an Attach does, so the Listing stays live while the user looks at it. Leaving the screen starts ADR 0012's 60 s idle rule. Going to the background still drops every Connection that no Attach holds.
- **Writes go on the channel with a Request id.** Every Host Write (ADR 0020) is a typed `environment` request that carries the Request id of ADR 0021. When the channel ends before the `end`, the phone sends the write once more, with the same id, on the next Host Server. The Host applies one id one time. The phone reads nothing after a write, because the subscription pushes the change.
- **Asked on the Host:** the Go to ranking (`session_paths { query }`, `visit_session_path`), a Topic's Add a Session rows (`session_paths { topic }`), a Window's Browser Tabs (`browser_tabs`), the Session choices of Forget (`topic_choices`), and Attachments (`upload`, up to 8 chunks in flight). Only two of the phone's own rules stay. Running Sessions come first in Go to, ranked by this phone's Recent Sessions, and only tailnet or public Tabs are shown (ADR 0017).
- **Sessions only.** The phone falls back to Sessions only when the Host has no Host Server, has one without the capabilities the phone needs (`request`, `snapshot`, `topic-detail`, `ranked-session-paths`, `browser-tabs`), stops 3 times within 60 s, or does not answer `hello` within 10 s. The Host Screen then shows the Sessions tab, read as today, and in place of Topics it says "Topics are unavailable on <Host>: <reason>", with the Mac's reasons. The Composer uploads with its script only in Sessions only. The next Connection tries the Host Server again. Nothing retries in the background.
- **The terminal stays on the Control Connection** (ADR 0006): the Attach, the Topology, Pane output, the Outbox (ADR 0022), Split and New Window once (ADR 0023), and switching Windows, Panes and Sessions. Pane output never crosses the Host Server, as on the Mac.

This changes ADR 0012's "Life" rule (a focused Host Screen holds the Connection) and its deadline rule for Host reads, which now go on the Host Server. It changes ADR 0016's "The Topics read does not wait" (the Host Server starts at once and starts again after an update). It changes ADR 0021's second send, which now goes to the next Host Server rather than as an exec, and its capability check, which now reads the server's `hello` rather than `environment show`. It changes ADR 0024's `session-paths --query` and `visit`, which are now asked over the channel.

## Considered Options

- **Keep the execs where protocol 1 has no request,** so that the set touches only the phone. Rejected: the phone would keep two ways to reach a Host for good, and the Host CLI's rules would stay copied on the phone.
- **Build the Listing on the phone from the raw `environment` events.** Rejected: it ports MuxifyCore's card and In Play rules to TypeScript. The Host already computes the snapshot that the phone draws.
- **Read `environment show` over the channel on every `environment` event.** Rejected: the phone would still decide when to read again. The Host knows when its snapshot changed.
- **Fall back to today's exec path when there is no Host Server.** Rejected: it keeps a second implementation of every Topic feature. The phone installs `cli-latest` on every Connection, so a Host without a Host Server is rare, and the Mac makes the same choice.
- **Writes on the channel with no Request id.** Rejected: a drop would leave every write unsure where ADR 0021 resends it safely today.
- **The phone uploads the Host CLI when the Host cannot download it** (the Mac's install chain B). Rejected for the reasons in ADR 0016.
